## 8. 협업 루틴 — 매주 반복하는 8 단계

7주차부터 최종발표까지 매주 같은 순서를 반복합니다: 이슈 → 브랜치 → 커밋 → 푸시 → 풀 리퀘스트 → 리뷰 → 병 합 → 정리. 수업 7·9주차 실습을 팀 저장소에서 그대로 하는 것입니다. 이 장을 프린트해서 모니터 옆에 두세요.

<a id="section-8-1"></a>

### 8.1 브랜치 규칙 (수업 7주차 '실습 브랜치 규칙'과 동일)

1\. main 브랜치에는 직접 커밋을 올리지 않는다 (동시에 작업하면 꼬인다)

2\. 기능 개발을 하기 전에 main 브랜치 기준으로 새로운 브랜치를 만든다

3\. 브랜치 이름은 feature/기능이름 형식으로 하고, 한 브랜치에는 한 명만 커밋한다

4\. 기능 개발이 끝나면 풀 리퀘스트로 main에 합친다 (9주차부터는 승인 1개가 있어야 병합됨)

| 브랜치 | 쓰임 | 예 |
| --- | --- | --- |
| main | 항상 실행되는 상태의 코드. 풀 리퀘스트로만 바뀜 | — |
| feature/기능이름 | 기능 개발 (수업 7주차 규칙. 12주차 예시의 feat/<br>도 같은 뜻 — 팀에서 하나로 통일) | feature/add-record, feature/monthly-<br>summary |
| fix/문제이름 | 버그 수정 | fix/csv-encoding |
| docs/내용 | 문서만 수정 | docs/readme-install |

브랜치 이름은 영문 소문자와 하이픈만 씁니다. 브랜치 하나의 수명은 1주가 적당하며, 길어지면 풀 리퀘스트를 나누 세요.

<a id="section-8-2"></a>

### 8.2 8단계 루틴 (소스트리 기준)

| 단계 | 소스트리·GitHub에서 하는 일 | 수업 |
| --- | --- | --- |
| 1. 이슈 | GitHub Issues에서 내가 할 일의 이슈를 확인(없으면 만듦, 8.4). 이슈 번호를 기억 (예: #12) | 3주차 |
| 2. 최신화 | 소스트리 사이드바 main 더블클릭(체크아웃) → 상단 Pull | 6주차 |
| 3. 브랜치 | 상단 브랜치 → 현재 브랜치가 main인지 확인 → 새 브랜치 이름 feature/기능이름 → 새 브랜<br>치 체크아웃 체크 → 브랜치 생성 | 7주차 |
| 4. 코딩·커밋 | VS Code로 수정·저장 → 소스트리 커밋 → 바뀐 파일을 +로 스테이지 → 메시지(8.3) → 커밋.<br>의미 있는 단위마다 반복 (하루에 여러 번) | 6주차 |
| 5. 확인·푸시 | 프로그램을 실행해 동작 확인 → 소스트리 Push → 내 브랜치 체크 → Push (또는 커밋 창의 -<br>에 바뀐 내용 즉시 푸시 체크) | 6~7주차 |
| 6. 풀 리퀘스트 | GitHub 저장소에 뜨는 Compare & pull request → base main ← compare 내 브랜치 확인<br>→ 제목·설명(8.5) → 오른쪽 Reviewers에서 팀원 1명 지정 → Create pull request | 9주차 |
| 7. 리뷰·병합 | 리뷰어가 Files changed 확인 → Review changes → Approve (고칠 것이 있으면 Request<br>changes). 수정은 같은 브랜치에 커밋·Push하면 풀 리퀘스트에 자동 반영. 승인되면 작성자가<br>Merge pull request → Confirm merge | 9주차 |
| 8. 정리 | 소스트리 패치(그래프 갱신) → main 체크아웃 → Pull → 다 쓴 브랜치 우클릭 → 삭제. 이슈는<br>풀 리퀘스트 설명에 Closes #12를 적었으면 자동으로 닫힘 | 9주차 |

<a id="section-8-3"></a>

### 8.3 커밋 메시지

- 한 줄, 한글로, '무엇을 했는지'가 보이게. 수업 6주차 예: OSS 혜택 및 할 일 목록 추가

- 권장 형식: 기능 설명 (#이슈번호) — 예: 거래 입력 기능 추가 (#12), 빈 파일 읽을 때 오류 수정 (#31)

- 수업 13주차의 분류 접두어(feat: 새 기능, fix: 버그 수정, docs: 문서, refactor: 구조 정리, test:, chore:)를 앞에 붙이면 이력이 더 읽기 쉬움 (선택)

- 커밋 1개 = 변경 1가지. 30분~2시간 단위가 적당. 수정, 최종, asdf 같은 메시지는 금지

- 메시지를 잘못 썼거나 파일을 빠뜨렸으면 새 커밋 대신 수업 12주차의 마지막 커밋 정정(어멘드)으로 고침 — Push 전에만

<a id="section-8-4"></a>

### 8.4 이슈

- 작업 전에 이슈를 먼저 만듭니다 (수업 3주차 '이슈 트래킹', 9주차 '이슈 트래커 검토'). 이슈 없는 풀 리퀘스트는 리뷰어가 '이슈 먼저 만들어 주세요'로 되돌림

- 제목: \[기능\] 월별 합계 계산, \[버그\] 한글 CSV 깨짐, \[문서\] 설치 방법 보강, \[질문\] 저장 형식 JSON vs CSV

- 본문 3줄: 목적(왜 필요한가) / 할 일(2~5개 체크리스트) / 완료 조건(무엇이 되면 닫는가)

- 오른쪽에서 Assignees(담당자)와 Labels(enhancement·bug·documentation·question)를 지정

- 크기: 이슈 1개 = 1~3일 분량. 담당 기능은 이슈 3~5개로 나눔

- 닫기: 풀 리퀘스트 설명에 Closes #번호를 적으면 병합 시 자동으로 닫힘

<a id="section-8-5"></a>

### 8.5 풀 리퀘스트 (수업 9·13주차)

| 항목 | 기준 |
| --- | --- |
| 단위 | 풀 리퀘스트 1개 = 이슈 1개. 한 번에 여러 기능을 담지 않기 (수업 13주차 '잘 쪼갠 PR') |
| 제목 | 커밋 메시지처럼 한 줄. 예: 거래 입력 기능 추가 (#12) |
| 설명 | 3줄: 무엇을 바꿨나 / 왜(Closes #12) / 어떻게 확인했나(실행 방법). 화면이 바뀌면 스크린샷 |
| 리뷰어 | 작성자 외 팀원 1명 이상을 Reviewers에 지정. 돌아가며 맡아서 한 사람에게 몰리지 않게 |
| 병합 | Approve 1개 + 충돌 없음 → 작성자가 Merge pull request(기본 방식 'Create a merge commit') →<br>Confirm merge |
| 기한 | 리뷰 요청 후 48시간 안에 리뷰. 늦어지면 팀장이 다른 리뷰어 지정 |

### 8.6 리뷰하는 법 (수업 7주차 '사람들이 중요하다', 9주차 '검토·개정·협업')

리뷰는 '틀린 곳 찾기'가 아니라 팀 코드를 함께 좋게 만드는 대화입니다. 15~20분이면 충분합니다.

1\. 풀 리퀘스트 설명과 연결된 이슈의 완료 조건을 읽음

2\. Files changed 탭에서 바뀐 부분을 읽고, 줄 번호 옆 +로 코멘트. 가능하면 브랜치를 소스트리로 체크아웃해 직접 실행해 봄

3\. Review changes → Approve(이대로 병합 가능) / Request changes(고친 뒤 다시 봄) / Comment(의견만)

| 확인할 것 | 질문 |
| --- | --- |
| 동작 | 이슈의 완료 조건을 만족하나? 실행해 보니 되나? 잘못된 입력에는 어떻게 되나? |
| 읽기 | 함수·변수 이름만 보고 역할을 알 수 있나? 너무 긴 함수는 없나? |
| 문서 | 사용법이 바뀌었으면 README도 바뀌었나? 새 라이브러리가 requirements.txt에 있나? |
| 안전 | 토큰·비밀번호·개인정보·큰 데이터 파일이 들어 있지 않나? |

코멘트 예: \[필수\] 파일을 열고 닫지 않아요. with open(...) 으로 바꿔 주세요. / \[제안\] 이 반복문은 sum()으로 한 줄 이 됩니다. / \[질문\] 날짜가 없는 행은 왜 건너뛰나요? / \[칭찬\] 오류 메시지가 친절하네요. — \[필수\]는 3개 이내로, 사 람이 아니라 코드에 대해 말합니다.

> \[참고\] 내용 없는 'LGTM'만 남긴 승인은 활동 규칙의 리뷰로 인정되지 않습니다. 실행해 봤다는 한 줄이나 구체적 인 코멘트 1개면 충분합니다.

### 8.7 충돌(Conflict) 해결 — 수업 9주차 '충돌 병합 해결하기'와 동일

두 사람이 같은 파일의 같은 부분을 고쳤을 때 GitHub 풀 리퀘스트에 'This branch has conflicts that must be resolved'가 뜹니다. 수업에서 배운 대로 내 브랜치에 main을 먼저 병합해 충돌을 해결한 뒤 Push하면 풀 리퀘스트 의 충돌 표시가 사라집니다.

1\. 소스트리 사이드바 main 체크아웃 → Pull (원격의 최신 main을 받음)

2\. 내 브랜치(feature/...) 체크아웃 → History에서 main의 최신 커밋 우클릭 → 병합 → 확인 → 충돌 경고가 뜨면 닫기

3\. 커밋하지 않은 변경 사항을 선택하면 충돌 난 파일이 스테이지 아래에 보임

4\. VS Code에서 그 파일을 열면 &lt;&lt;&lt;&lt;&lt;&lt;&lt;, =======, &gt;&gt;&gt;&gt;&gt;&gt;&gt;로 두 버전이 표시됨. 위쪽은 내 브랜치, 아래쪽은 main의 내용. 충돌 부분 위에 뜨는 메뉴(현재 변경 사항 수락 / 수신 변경 사항 수락 / 두 변경 사항 모두 수락)를 고르거나 손으로 정리해 표시 줄을 지우고 저장

5\. 프로그램을 실행해 정상인지 확인 → 소스트리에서 파일을 스테이지에 올림 → 커밋 (메시지 자동 입력, 그대로 두어도 됨) → Push

6\. GitHub 풀 리퀘스트에서 충돌 표시가 사라졌는지 확인 → 리뷰 → 병합

### 8.8 자주 하는 실수와 복구 (수업 12주차 '실무 사례와 함께 Git 다루기' 기능 활용)

| 상황 | 복구 방법 |
| --- | --- |
| 방금 커밋에 파일을 빠뜨렸거나 메시지를<br>잘못 씀 (Push 전) | 빠뜨린 파일을 스테이지에 올리고 커밋 옵션 → 마지막 커밋 정정(어멘드) → 커밋. 이미<br>Push한 커밋은 정정하지 말고 새 커밋으로 |
| main에서 그냥 작업하고 커밋함 (Push 전) | 소스트리 브랜치로 새 브랜치 feature/...를 만들면 그 커밋이 새 브랜치로 감 → main은<br>origin/main 커밋 우클릭 → 이 커밋까지 현재 브랜치 초기화(Hard)로 되돌림 |
| Push가 거부됨 (rejected) | Pull → 충돌이 있으면 [8.7절](08-collaboration.md#section-8-7) → Push. 강제 푸시는 나 혼자 쓰는 브랜치에서만(수업 12<br>주차), main에는 절대 금지 |
| 병합된 커밋·풀 리퀘스트를 되돌리고 싶음 | 공용 브랜치에서는 리셋 대신 리버트: 소스트리에서 커밋 우클릭 → 커밋 되돌리기, 또는<br>GitHub 닫힌 풀 리퀘스트의 Revert 버튼 → 되돌리기 풀 리퀘스트 (수업 12·13주차) |
| 급한 버그 때문에 다른 브랜치로 가야 하는<br>데 작업 중인 파일이 있음 | 소스트리 스태시에 잠시 넣어 두고 브랜치 이동 → 돌아와서 스태시 적용(적용 후 삭제 체<br>크) (수업 12주차) |
| 다른 브랜치의 커밋 하나만 내 브랜치에 필<br>요함 | 그 커밋 우클릭 → 체리 픽 (수업 12주차). 자주 쓸 일은 없음 — 보통은 풀 리퀘스트로<br>main에 합친 뒤 Pull |
| 토큰·비밀번호·개인정보를 커밋함 | 파일을 지우고 다시 커밋해도 이력에 남음 → 해당 토큰을 즉시 재발급(GitHub 토큰은<br>Settings → Developer settings에서 삭제). 앞으로는 [9.5절](09-python.md#section-9-5) |
| 소스트리 그래프에 GitHub 병합 결과가 안<br>보임 | 패치(fetch)로 그래프 갱신 → main 체크아웃 → Pull (수업 9주차 실습 8~12단계) |
| git merge 뒤 검은 화면(vim)에 갇힘 | Esc → :wq → Enter. [6.3절](06-tools.md#section-6-3)의 core.editor 설정을 하면 VS Code가 대신 열림 |
